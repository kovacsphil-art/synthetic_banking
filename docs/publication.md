# Automated showcase publication

**Post-pilot publication verified:** [Actions run](https://github.com/kovacsphil-art/synthetic_banking/actions/runs/44848318450) completed both preparation and Pages deployment successfully. The [live Validation Report](https://kovacsphil-art.github.io/synthetic_banking/validation.html#summary) was checked against its sanitized JSON: 10,000 customers, 17,313 accounts, three applied rules, mean/tail screens and privacy REVIEW_REQUIRED. The report retains its original validation completion timestamp; refreshing reporting did not regenerate the cohort. General privacy clearance remains blocked; the separately verified DEMO_ONLY download integration described below is now live. Future successful reports use the same automated path; no new credentials or settings are required for this update.

The static site is published by `.github/workflows/publish-showcase.yml`. GitHub checks Databricks every 15 minutes (at minutes 7, 22, 37 and 52 UTC) and can also be triggered manually. GitHub schedules can be delayed; this is polling, not an immediate callback. This workflow does not start the banking pipeline or approve proposals.

```text
Databricks generation → privacy screen → GENERATED profile → validation PASS
  → reporting succeeds: run-specific sanitized JSON + private path receipt
  → GitHub Actions verifies completed job and every expected task succeeded
  → select latest successful validation → download its checksum-bound JSON
  → closed-schema + browser checks → optional separately verified demo Release
  → stage/check exact public artifact → commit public metadata → upload → GitHub Pages
```

## One-time setup

1. Merge these changes onto the repository's default branch. Deploy the updated Databricks bundle using [the workflow instructions](workflow.md). Its reporting task now receives `{{job.run_id}}` and writes `<report_output_dir>/runs/<job-run-id>/latest-pipeline.json`. The notebook returns a private receipt via `dbutils.notebook.exit`; the receipt is never committed or deployed. Interactive reporting without a job ID retains the original output location.
2. In Databricks, create a service principal and OAuth M2M secret. Assign it to the workspace, give it **CAN VIEW** on this job and the required **USE CATALOG**, **USE SCHEMA**, **READ VOLUME** permissions on the reporting Volume. Use a separate reporting-only Volume so this identity cannot read source or synthetic datasets. The pipeline identity needs writes there. The GitHub runner must be able to reach the workspace's API; private networking needs an appropriately secured runner.
3. Under GitHub **Settings → Secrets and variables → Actions**, add repository secrets `DATABRICKS_HOST` (workspace HTTPS URL), `DATABRICKS_CLIENT_ID` and `DATABRICKS_CLIENT_SECRET`. Add repository variables `DATABRICKS_JOB_ID` (the deployed job's numeric ID) and `REPORT_OUTPUT_DIR` (the same absolute `/Volumes/...` directory as the bundle variable). No GitHub credential is stored in Databricks. Rotate the OAuth secret through GitHub Secrets.
4. Under **Settings → Pages → Build and deployment**, choose **GitHub Actions**. Configure the `github-pages` environment to permit the default branch. Allow the workflow's built-in `GITHUB_TOKEN` to write repository contents. Branch rules must allow its single-file report commits; if policy forbids this, the workflow stops before deploying. No force pushes or protection bypass is implemented.
5. Run the updated Databricks pipeline successfully. A batch waiting for manual review is intentionally failed and cannot publish. Review and repair it using the existing procedure. No new proposal is automatically approved.

For Databricks Free Edition, use the workflow runbook's `free` serverless bundle target rather than supplying a classic cluster ID. The GitHub repository must be public to use Pages on GitHub Free. The `free` target affects compute configuration only; review, validation and publication gates remain in place.

GitHub uses its short-lived `GITHUB_TOKEN` for the report commit and Pages OIDC for deployment. No personal GitHub token is needed. The reporting SDK and JSON Schema validator are pinned in the workflow. Credential values are scoped to the retrieval step, never passed in shell arguments, committed, or placed in a Pages artifact.

## Manual trigger

Open **Actions → Publish validated showcase → Run workflow**, choose the default branch, and optionally enter a successful Databricks **job run ID** (not a task ID or profile ID). Blank scans retained completed run metadata and selects the eligible run with the latest final successful `validate` task completion, breaking timestamp ties by numeric job-run ID. Start order and reporting-only repair time do not decide the baseline. Failed/cancelled runs and incomplete historical task graphs do not qualify. Missing validation-completion metadata stops automatic publication rather than guessing. This also works after repairing an approval stop. Older validation timestamps cannot roll back the report already in Git. The manual trigger performs publication only; start the Databricks job separately using Jobs & Pipelines or the bundle CLI.

From an authenticated CLI, `gh workflow run publish-showcase.yml --ref main` exercises the same automatic selection used by the schedule. Add `-f pipeline_run_id=<JOB_RUN_ID>` only when selecting a particular completed execution. Zero, negative and nonnumeric IDs cannot silently select another run.

## Publication boundary and failure behavior

- Only the configured job with overall SUCCESS and all nine expected successful tasks (or the original eight for legacy aggregate-only runs) qualifies. If the API includes retry/repair history, the final attempt for each task must succeed; earlier failed attempts do not invalidate a repaired success. Attempt timestamps must make the ordering unambiguous. The downloader reads only the final reporting task's receipt, then the exact run-specific Volume file. Every receipt must contain a valid SHA-256 matching the downloaded bytes, including aggregate-only reports. It never retrieves notebook logs or SOURCE/Delta rows. Only the explicitly enabled verified demo branch may additionally download its fixed run-scoped CSV/ZIP assets from the reporting Volume. Older runs without a checksum receipt must repair reporting with the current Notebook 06; if snapshot/lineage checks no longer hold, complete a new pipeline run instead. Do not manufacture a receipt or copy another run's report.
- Payloads must pass the closed version-1 or version-2 JSON Schema (no extra fields), size limit, timestamp validation and browser contract. Fixed warning wording replaces incoming free text. Version 2 adds the [detailed validation report](validation-report.md); version 1 leaves that page in its pending state. Unknown contract changes stop publication. Only the report is staged in aggregate-only mode; verified demo publication additionally stages its matching bounded preview and download manifest.
- The Pages artifact allowlist contains `index.html`, `styles.css`, `results.js`, `validation.html`, `validation.js`, `validation-config.js`, `executive-viz.js`, `showcase.js`, `latest-pipeline.json` and `.nojekyll`. The prepared record-explorer extension adds `records.js`, `records-config.js` and optional, separately verified `demo-preview.json` (at most 15 fabricated records per table and 96 KiB). Preview absence leaves an unavailable state; a present invalid preview stops preparation. The prepared download extension adds `downloads.js` and optional `dataset-downloads.json` (at most 16 KiB of verified file metadata). The browser checks version-pinned GitHub Release assets before enabling links; automatic asset uploads require the explicit demo-publication variable. With `SAGE_PUBLISH_DEMO_DATASETS=true`, the publisher retrieves only the successful run's independently verified demo copies from the reporting Volume; it never reads SOURCE/generated Delta tables or private export directories. No access grants are changed by this code. CSVs, ZIPs, the export folder, notebooks, source code, internal reports and documentation examples are never copied into Pages. See the [preview contract and publication hold](records-preview.md).
- Failed/cancelled/pending Databricks runs cannot replace a report. A failed JSON build leaves prior reports intact; missing/invalid downloads or failed Git pushes stop deployment. Pages keeps its existing deployment if preparation or deployment fails. If a commit succeeds but Pages deployment fails, rerun the workflow: unchanged reports still deploy, which repairs that partial failure.
- A schedule may republish the same valid report, including reviewed website asset changes on the default branch. Selection uses the final validation completion, and the public completion-timestamp guard independently refuses a regression. A reporting-only repair of an older validation cannot take precedence over a later validated cohort. Concurrency serializes publication; competing human pushes cause a safe push failure and require a retry.
- Privacy findings may block row distribution while the aggregate site still publishes. Public integrity PASS is not privacy clearance. The optional verified DEMO_ONLY branch uploads all eight assets to a draft versioned Release, publishes only after complete verification, then commits matching metadata. It is disabled unless both the Databricks opt-in and GitHub publication switch are satisfied; see [automated demo publication](automated-demo-publication.md).

GitHub may disable scheduled workflows in inactive public repositories; re-enable the workflow or trigger it manually. Changes committed with `GITHUB_TOKEN` do not need to trigger another workflow: the same run builds and deploys Pages. Investigate failures in Actions; rejected payloads and SDK exception details are deliberately omitted from logs.

## Checks and operating limits

Every publication now runs the Python publisher/staging safeguard tests and the dependency-free frontend suite before credentials are supplied to report retrieval. `scripts/stage_showcase.py` replaces shell copying with an explicit allowlist. It revalidates/sanitizes the one report, checks required local HTML assets, rejects symlinks, external asset references and oversized assets and refuses an existing staging destination. In demo mode it also checks the closed preview/manifest schemas, hash, version, privacy status, six table counts and canonical version-pinned URLs. Without that explicit mode neither demo JSON file enters Pages, even if stale copies remain in Git. CSVs, ZIPs, secrets, notebooks and internal reports never enter the Pages artifact. Staging is a consistency check, not an alternative fabricated-origin authorization.

The browser contract is checked again against the **staged** files before any metadata commit or artifact upload. The workflow summary records the sanitized report hash and whether gated demo metadata was included. A failure in tests, retrieval, schema checks, Release verification, staging or Git push prevents deployment. Native Pages deployment replaces the served artifact only when deployment succeeds; no in-place editing of the live site occurs. A preparation failure can leave ignored scratch, and a commit followed by a deployment failure can leave newer metadata in Git; the live site retains its prior artifact and a retry repairs publication. An already completed verified Release remains separately public if a later Pages step fails; the workflow does not claim a cross-service atomic transaction.

Both pages derive their measured charts/cards from one sanitized JSON load. The overview's hero, findings and distribution preview share that report object; the Validation Report normalizes one report object. Demo components independently require their manifest/preview/report bindings to agree, so a partial fetch across deployments disables demo controls rather than mixing cohorts. No HTML edit is required when a successful pipeline supplies new data.

Run `python -m pip install jsonschema==4.23.0` for local publication tests, then the normal Python suite with the repository root and `src` on `PYTHONPATH`. The new tests use fabricated metadata and the documented example. No live workspace or deployment is needed for them.

The repository's existing Pages/Actions setup and reporting-only Volume are reused. The post-pilot bundle deployment and reporting-only repair succeeded against the same validated cohort. The public contract now includes optional measured mean/tail screens and a separate REVIEW_REQUIRED privacy summary, with standard row-release clearance unchanged and demo eligibility assessed separately. Deploy schema/browser changes on the default branch before retrieving that extended report. Use the Actions run's **deploy** result and the live JSON to verify publication; a local commit or successful Databricks export alone is not evidence of a Pages deployment. Retain the per-run Volume artifacts while GitHub needs them; use your normal retention policy afterwards. Continue testing failed validation/report writes and repaired runs in a test destination.

## Configuration status and external setup

For the existing SAGE repository, the three Databricks secret **names**, three variable names, active publication workflow and GitHub Actions Pages source were checked. Secret values were not read or printed. Existing successful publications demonstrate the configured OAuth/job/Volume access. This publisher-only update requires no Databricks modeling or bundle change in that already deployed environment.

For a new installation, these steps need account/workspace access and cannot be completed by editing local files alone:

| System | Required setup |
| --- | --- |
| Databricks | Deploy the existing bundle; retain exact-ID task handoffs and Notebook 06's checksum receipt. Provision the reporting Volume and give the pipeline write access. |
| Databricks publisher identity | Workspace service principal with OAuth M2M, CAN VIEW on the one pipeline job and USE CATALOG / USE SCHEMA / READ VOLUME on its reporting destination. No SOURCE/generated-table SELECT grants are needed. If demo publication is enabled, this approved Volume also holds verified fabricated demo copies; see the separate demo runbook. |
| GitHub Secrets | `DATABRICKS_HOST`, `DATABRICKS_CLIENT_ID`, `DATABRICKS_CLIENT_SECRET`. Configure through Secrets, never tracked files, HTML, shell arguments or Databricks notebook output. Rotate the OAuth secret before expiry. |
| GitHub Variables | `DATABRICKS_JOB_ID`, `REPORT_OUTPUT_DIR`. Optional `SAGE_PUBLISH_DEMO_DATASETS=true` only for the separately authorized fabricated-demo branch. Match the deployed reporting directory exactly. |
| GitHub Pages / Actions | Pages source = GitHub Actions; enabled workflow on the default branch; github-pages environment permits deployment. Existing preparation contents:write and deployment pages:write / id-token:write permissions must be allowed by repository policy. |
| Network / operations | Runner can reach the Databricks API. Maintain Volume retention, service-principal access, credential rotation and schedule availability. Human proposal approval still happens in Databricks; publication never approves rules or starts generation. |

Automated updates use the existing 15-minute polling schedule after successful pipeline execution; they are not an instant Databricks callback. GitHub can delay scheduled jobs or disable schedules in inactive public repositories. Re-enable the workflow or use the manual trigger when needed. The next successful validated run needs no HTML editing, file copying or manual Release upload.

## Optional DEMO_ONLY Release branch

See [automated demo publication](automated-demo-publication.md) for the nine-task graph, exact lineage, draft upload/repair semantics and both disable switches. `SAGE_PUBLISH_DEMO_DATASETS` defaults off. Setting it to true expands the contents intentionally handled by this existing publisher from aggregates to fully verified fabricated demo records in the same reporting Volume; no new Databricks permissions or GitHub secrets are created.
