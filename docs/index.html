Architecture

Pipeline

Three notebooks connect statistical measurement, AI proposals, and Python generation. Human review controls which supported proposals can run.

One consistent baseline

SOURCE is the original profiling baseline. GENERATED is the separate profile of synthetic output. A pinned baseline means every stage uses the same explicitly selected, completed SOURCE run.

Notebook 01

Statistical profiling

The profiler stores reusable aggregate measurements in Delta. SOURCE and GENERATED runs keep separate histories so their statistics can be compared.

Numeric distributions
Quantiles, mean, spread, and bounds describe how numeric values are distributed.
Categorical proportions
Observed category frequencies provide weights for sampling categories.
Null rates
Column quality records missing values, row counts, and distinct counts.
Date ranges
Earliest and latest observed dates define generation bounds.
Cardinalities
Relationship counts describe structure, such as how many accounts belong to a person.
Dependency statistics
Selected correlations, utilization-bucket delinquency rates, and bounded categorical cross-tabs with Cramér's V describe relationships.
How profiles guide sampling

Numeric generation approximates an inverse cumulative distribution using profiled quantiles. A quantile is a cutoff in a distribution, such as the median or 95th percentile. Categorical sampling uses observed proportions. Dates use SOURCE month proportions and feasible ordering bounds.

The profiler supplies measured distributions and probabilities. The LLM proposes which dependencies may matter.

Notebook 02 + human review

AI & review

The Databricks-hosted LLM proposes candidate dependencies and rules. Its input consists of aggregate profiler metadata, with row-level banking records kept outside the prompt.

LLM-generated text is never executed directly.

Approved metadata can select a predefined Python implementation when the target, rule type, parent columns, and review provenance match.

From proposal to execution

  1. Proposed

    Candidate metadata and evidence are saved in a batch tied to the SOURCE profile shown to the model.

  2. Manually reviewed

    A reviewer inspects the candidate and records an individual decision.

  3. Approved

    The review state is APPROVED. PENDING and REJECTED proposals are skipped.

  4. Implemented

    A fixed registry matches the supported target, type, and input columns to known Python code.

  5. Applied

    The execution audit records whether that implementation generated values for at least one row.

Approval and execution are separate

An approved proposal without a matching implementation is logged and skipped. A target without a unique eligible approval uses the existing generation path.

The audit distinguishes applied, skipped, and legacy fallback outcomes. A fallback is an existing formula used to supply a target.

What the LLM receives and proposes

Inputs include column roles, numeric quantiles, null rates, and category proportions.

Each proposal identifies its target, rule type, parent columns, and supporting evidence. Parent columns are the inputs used by a rule.

Controlled pilot

The pilot connects reviewed proposals to two balance formulas already implemented in Python. Both depend on credit limit and current balance.

A manually approved proposal can select predefined sampling from measured SOURCE delinquency rates by utilization bucket. Missing evidence produces a logged skip. Without an eligible approval, the existing generation path supplies the outcome.

Saved outputs + Notebook 01

Validation & results

Saved outputs pass validation before GENERATED profiling. The same profiler then compares generated statistics directly with the pinned SOURCE baseline.

Project methodology

What validation checks

  • Required columns and compatible types
  • Synthetic identifiers, row counts, and parent keys
  • Full account-to-balance snapshot join coverage
  • Derived-rule invariants and the rule execution audit
  • Successful Delta writes and validated table versions
Why account-to-balance alignment matters

Accounts and balances share ACCOUNT_ID and BUSINESSEFFECTIVEDATE. Matching both fields keeps dependency checks aligned with the generated account population.

How to read and refresh these results

SOURCE is the selected baseline. GENERATED is the synthetic-data profile compared against it. Quantiles show cutoffs in a distribution. Utilization is balance relative to credit limit, and past-due rates are grouped by utilization range.

Differences are GENERATED minus SOURCE, in the measurement’s native units. Rate differences use percentage points. Unavailable indicates a missing or undefined measurement. Integrity checks and statistical fidelity are separate: no overall fidelity acceptance threshold is configured.

The workflow’s final reporting task exports sanitized aggregate JSON after validation succeeds. Publish that file as latest-pipeline.json beside this page, then choose Refresh results. The timestamp identifies the last successfully validated export; the page does not connect directly to Databricks.

Prototype scope

Limitations & next steps

Most fields still use marginal sampling. Numeric distributions use percentile approximations. Dates use day precision, with uniform sampling within each supported month and explicit ordering constraints.

Broader dependencies
Extend measured relationships and the controlled registry beyond the balance formulas and utilization-conditioned delinquency. The AI stage currently covers the two account tables.
Categorical relationships
Use the measured cross-tabs and association diagnostics to extend controlled generation beyond independent categorical sampling.
Customer relationships
Review measured degree, direction, type and null-pattern fidelity from the new CUSTOMER_RELATIONSHIP generator. Extend demographic and ownership-network modeling.
Stronger validation
Expand comparisons of distributions, null rates, dates, cardinalities, and conditional outcomes.
Privacy testing
Evaluate disclosure and re-identification risks alongside statistical utility.
